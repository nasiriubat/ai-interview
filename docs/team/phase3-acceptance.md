# Phase 3 acceptance: can an agent build from a generated bundle?

Phase 3's acceptance criterion (`docs/spec/15-phase-plan.md`) has two halves. This records the
second: **a coding agent builds a sample feature from the bundle without asking a question.**

## The test

Run on 2026-09-14 against the live stack (OpenRouter, Claude Sonnet 5 for turns and issue
detection, Claude Opus 5 for generation).

1. A nontechnical requirements interview produced a specification for a small internal
   hospital tool ("Ward Charting Single Entry"): 57 turns, 48 spec fields, 6 findings raised
   and settled in the conversation, the MVP challenge over all three MVP items.
2. Version 1 was generated by the worker: 16 sections, 8 requirements, 4 phases, 5 Mermaid
   diagrams, a 9-file agent bundle.
3. The bundle alone (`AGENTS.md`, `PLAN.md`, `tasks/phase-*.md`, `spec.md`, `spec.json`) was
   handed to a coding agent with no access to the interview, the product, or the author, and
   it was asked to build the most substantial phase 1 feature and to log every decision the
   bundle did not settle.

## Result

The agent built tasks 1.5 (single-entry form and write to the patient system) and 1.6 (failure
handling, local cache, retry queue) as a TypeScript project with 16 tests, one per acceptance
criterion, all passing. It reported:

| Outcome   | Count | Meaning                                                                  |
| --------- | ----- | ------------------------------------------------------------------------ |
| Answered  | 14    | The bundle settled it; the agent quoted the line                         |
| Defaulted | 5     | The bundle recorded a default under Open questions and the agent took it |
| Blocked   | 9     | The agent had to invent something the author should have decided         |

Verdict: **not yet**. Everything a nurse would notice was pinned down, including both banner
texts verbatim, the validation ranges, the retry backoff schedule, the idempotency key, the
persist-then-call ordering and the device and ward gates. Three blocked items would still have
forced a question:

1. **An integration named without its contract.** The patient system write is described by the
   data that flows, not by an endpoint, payload shape, authentication or error shape. The spec
   flags the _read_ endpoint as pending confirmation and is silent that the write contract is
   equally unknown.
2. **A failure path with no permanent-failure case.** The business rule says the tool retries
   "until it succeeds". Read literally, an observation the patient system rejects as malformed
   sits invisible in a retry loop for 24 hours. Clinically significant, and the author was
   never asked.
3. **A state used but not defined.** The observation lifecycle diagram has a `Flagged` state
   and an acceptance criterion requires flagging, but the data model's `status` enum does not
   contain it.

The remaining six blocked items (temperature rounding, the anchor of the 24-hour window, when
the audit row is written, field-level validation wording, the synchronous write timeout, the
stored status after a failed attempt) are the ordinary residue of any specification and did not
stop the build.

## What changed as a result

The three blocking items are exactly what the issue-detection pass exists to catch, and it
missed all three while finding six others. The `issues` prompt is now at v2 and looks
explicitly for: an integration named without its contract; a retry path with no permanent
failure case; a state used in a diagram or acceptance criterion that the data model does not
define; a numeric promise a requirement depends on that no decision records; and the same
thing recorded differently in two sections. The prompt also carries the acceptance criterion
itself as its test: could a developer implement this without asking the author?

Re-running the same interview against the v2 prompt, and confirming those three findings are
raised, is the next step before this criterion is called met.

## The other half: regenerating this specification

The first half of the criterion is "this spec is regenerated by the product from a rough prompt
and diffs cleanly against these documents". Run on 2026-09-14 from the verbatim intake in
`docs/discovery/00-intake.md` (one paragraph, two sentences of product plus the meta-request),
on the technical path, with a harness that answered the question actually asked from the
decision log and otherwise said "take the option you would recommend".

80 turns, 98 spec fields, 11 findings all settled, the MVP challenge over 9 items, 15 of 16
areas covered. The generated version: 17 sections, 18 requirements, 4 phases, 6 diagrams,
66 KB of `spec.md`.

Against the 36 decisions in `docs/discovery/decisions.md` and the frozen spec, 32 are present,
including the ones that matter most: templates as data, layered context with a rolling summary
and recall, seven-factor scoring with k-anonymity, one response per person with a salted email
hash, per-purpose model routing with a ledger and enforced budgets, Fastify plus worker,
Next.js, Postgres with pgvector, pg-boss, Docker Compose on an EU VPS, row-level tenancy, and
a phase order that matches the real plan (foundations, core interview, analysis, requirements
interview).

Four are missing, and all four are things the owner never volunteered and no coverage area
asks for: the turn object and its widgets, path selection and the context block, the "an agent
builds from it without asking" acceptance criterion itself, and the decision to use no agent
framework (mentioned once, not recorded as a decision). They are product internals a customer
would not raise unprompted; the template would need a coverage area that asks how the product
itself behaves turn by turn.

One defect this exposed and fixed: requirement ids drifted from `FR-1` into descriptive slugs
(`FR-campaigns`, `FR-budget-enforcement`) after the first few. Phases, tasks and commit
messages reference those ids, so they must stay short and sequential. The interviewer prompt
is now v4 and says so explicitly.

This is not a like-for-like comparison and should not be read as one: `docs/spec/` came from
three rounds of interviews with a person plus design discussions, and this came from one
paragraph and a scripted interviewee in about forty minutes for roughly two euros of model
spend. The honest reading is that the product recovers most of a specification from a rough
prompt, and misses what nobody tells it.
