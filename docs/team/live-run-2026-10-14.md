# Live pipeline run, 2026-10-14

A real end-to-end run on OpenRouter with cheap models, driven by `pnpm live:run`
(`scripts/live-run`): eight simulated employees through discovery interviews, analysis, promotion
into a requirements session, a nontechnical and a technical owner interview, spec generation,
bundle export and a version diff. About 2.5 USD across five full runs; the final run cost about
55 cents in the ledger and 15 cents in simulators and judge.

The run executed on code from before the M1 merges. The triage column says what the merged tip
already fixes; **the harness must be re-run on the tip** to confirm.

## Models used (USD per million tokens, input / output)

| Purpose                                                                 | Model                                    | Price        |
| ----------------------------------------------------------------------- | ---------------------------------------- | ------------ |
| interview_turn                                                          | anthropic/claude-haiku-5.5               | 0.10 / 0.50  |
| resume_summary, extraction, issue_detection, file_ingest, vision_ingest | mistralai/mistral-small-3.2-24b-instruct | 0.094 / 0.25 |
| clustering, analysis_report, spec_turn, spec_generation                 | openai/gpt-4.1-mini                      | 0.40 / 1.60  |

Reasoning-capable models failed: haiku spent hidden output tokens and was cut off at max_tokens in
74% of extraction calls; deepseek-v4-pro was cut off in clustering and produced corrupted spec
markdown. The 400-cent tenant budget held with no overrun.

## What worked

All 8 interviews ended through the engine at 20 to 24 turns, 5 to 44 facts each, cost 1.4 to 2.2
cents per interview. No where-should-AI-go questions, no participant names in the report, all
seven report sections present, anonymous transcripts unreadable by staff by default, delete-my-data
worked, budget enforcement worked, exports returned 200. First token p50 2.7 s (discovery) and
3.9 s (requirements).

## Prompt-quality findings

- Formulaic openers: nearly every message begins "Thanks," or "Got it," and often the first name.
  Forbid repeating an acknowledgement and use the name at most once.
- Compound questions: "When was it due, when did it reach you, and what did you do while you
  waited?" Require exactly one interrogative per message; a heuristic found 1 to 4 per interview.
- Requirements interviewer: good defaults with consequences, but 17 of 71 messages had two
  question marks ("question, then confirm default").
- Extraction prompt says "facts already known (do not repeat): N" but passes only a count, so
  duplicates cannot be avoided. Pass a compact list.
- Clustering prompt demands every id echoed; switch to merges over draft ids.
- Spec prompt: state the output language and reject non-ASCII headings (a Chinese-headings run
  occurred with one model, unconfirmed).

## Readiness verdict at the time

Not ready for a pilot: bugs 1 to 4 made finishing and session state unreliable and facts silently
dropped; bug 5 broke analysis at pilot scale. Bugs 1 to 4 are addressed on the tip; 5 to 8 and the
prompt changes are the next work item. Re-run with `pnpm live:run` (about 45 minutes, about 70
cents); environment overrides are documented in `scripts/live-run/README.md`.

## Re-run on the pipeline branch (bugs 5 to 8 and the prompt changes)

the second after the merge of configuration M2 and two fixes the first run exposed: a 404 from a
route without the reasoning control was not retried without it (two jobs failed), and a model
`reason` longer than 300 characters failed a whole turn. Spend: about 0.50 USD in the ledger and the
key per run, 0.11 USD of simulators and judge, and 0.07 USD for the scale check below; about 1.3 USD
in all. Run 1 is "after (1)", run 2 "after (2)".

Read these honestly:

- **Clustering at scale.** The live campaign is 228 to 256 facts, below the 441 that broke the
  old pass, so the real campaign does not prove it. `evals/live/scale.live.ts` replicates the facts
  of a run to 500 (each copy a different participant) and runs the real pipeline against
  gpt-4.1-mini: every fact in exactly one cluster, 46 clusters, 40 opportunities, 50 model calls
  (5 clustering, 45 report), 49 s, 6.6 cents, no failed opportunity. The largest cluster holds 132
  facts: lexical vectors chain, which a real embedding route would not (OpenRouter serves none).
  The copies are not new interviews, so this shows the pass completes and stays bounded, not that
  the clusters are good at 500 distinct facts.
- **Reasoning.** Requests to OpenRouter carry `reasoning: { effort: "none" }`. Probing haiku with
  and without it returned the marker and valid metadata both ways; no truncation at max_tokens was
  seen in either run (74 percent of extraction calls before, with the other model).
- **Metadata warnings went up, not down.** 128 to 135 turns had no marker, and about half of them (69 of 135 in run 1)
  are requirements turns on the strong route (gpt-4.1-mini), the rest haiku discovery turns. The parser did not
  lose them (no marker text leaked into any stored message: 0 of 255); the repair call rebuilt the
  metadata for those turns. Before, each of those turns lost its delta. The rate itself is a
  property of the models; a different route for `spec_turn` is the lever.
- **Requirements spec counts fell from 6 and 8 to 1 and 1 in the second run.** In that run the
  nontechnical session recorded 168 spec fields and none under `functional` (140 under `rules`),
  and the technical one a single `FR-2`. The same prompt produced 6 and 8 in the first run, so
  this is model variance in what it files under which section, not a code regression, but it means
  one run proves nothing about requirement capture and the repair prompt (which does not rebuild
  `facts`) cannot help it. Worth a deterministic check that a finished session has requirements.
- **Interviewer messages.** Compound questions persist at a low rate (the model still writes
  "which ward do you work on, and what are your responsibilities"); the judge counted 0 to 1 of 160
  not single-question, the heuristic 7 to 11. Openers and name use were not measured separately.
- **Ledger.** Rejected strict-schema attempts are rows with zero tokens, so a route that refuses
  strict `json_schema` still shows as error rows; they appear once per concurrent first call (the
  memory is per adapter and the four opportunity calls start together), not on every call. The
  Anthropic-on-OpenRouter route no longer pays the round trip at all.
- **Reopen** is covered by unit tests of the state transition and the flow of the diff; the live
  harness does not reopen a session, so it is not exercised live.

Failures that remain: one `GET /p/session` 401 (the delete probe, expected), one worker job that
failed in each run (an extraction retried by the queue), and the 140-rule drift above.

## Requirements capture variance: before and after the turn contract (D-190 to D-193)

Measured with `evals/live/variance.live.ts`: the real engine, extraction, rolling summary and spec
generation against OpenRouter, the shipped nontechnical owner persona of `scripts/live-run` as the
simulated participant, an in-memory store. Five interviews of 48 assistant turns each, same models
both times: interview turns `anthropic/claude-haiku-5.5` (0.10 / 0.50 USD per Mtok), summary,
extraction and issue detection `mistralai/mistral-small-3.2-24b-instruct` (0.094 / 0.25), spec
generation `openai/gpt-4.1-mini` (0.40 / 1.60), simulator `qwen/qwen3-30b-a3b-instruct-2507`. "Before"
is the tip at `2f1df59` (extracted from git into a scratch directory, the same script copied in);
"after" is this branch. "Parse failure" is a reply with no recoverable metadata at all (the engine's
"turn metadata not parsed" warning, counted identically in both). "Unrecovered" is a parse failure
with no successful repair call (ledger rows of `turn_meta_repair`).

| Measure (5 runs)                            | Before                       | After               |
| ------------------------------------------- | ---------------------------- | ------------------- |
| Requirements recorded (min / median / max)  | 0 / 1 / 5                    | 25 / 32 / 45        |
| Requirements in the generated spec          | 1 / 3 / 9                    | 25 / 32 / 45        |
| Spec fields under `rules` (min / med / max) | 0 / 2 / 4                    | 5 / 9 / 11          |
| Assistant turns                             | 22 (timeout), 48, 48, 48, 48 | 48 each             |
| Parse failures / turns                      | 145 / 214 (67.8 percent)     | 0 / 240 (0 percent) |
| Unrecovered parse failures                  | 0                            | 0                   |
| Repair calls                                | 145                          | 8                   |
| Generated version failed loudly             | 0                            | 0                   |
| Cost, product ledger + simulator            | 0.344 + 0.095 USD            | 0.439 + 0.106 USD   |

Read these honestly:

- **The criterion is met:** minimum 25 recorded requirements (needed: 5), contract failure rate 0 of
  240 turns (needed: under 2 percent). Before, one interview recorded 0 requirements in 22 turns while
  the generated spec held 4 (the model wrote them from the summary), and two held 0 and 1.
- **The marker was missed in 68 percent of haiku replies, not 50.** Cause: the interviewer's earlier
  messages are shown to the model without their metadata block, so it imitates its history. A format
  reminder as the last line of the engine focus took it to 0 of 240; the repair call fired 8 times for
  other reasons (an answer that recorded no spec field, a rejected fact).
- **The new numbers are high, and not all of them are good.** Median 32 requirements for a ward-notes
  tool is more than a person would list. Extraction now files every extracted spec fact as an FR and
  the capture rules say every capability is its own requirement; duplicates and fine-grained items are
  likely. Nobody has judged these 160 requirements for quality, and `rules` also went up. Reading a
  few specs and tuning the extraction wording or de-duplicating by meaning is the next step; the
  gate cannot see it.
- Five runs of one persona on one model pair is a distribution estimate, not a proof. One "before"
  run ended at turn 22 on a provider timeout (the harness does not retry a turn).
- Total live spend of this work: about 1.05 USD (the two runs above and three short probes), under
  the 1.5 USD cap.
